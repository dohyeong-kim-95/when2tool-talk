벤치마크 기존 도구 벤치마크(ToolLLM, BFCL 등)는 "모든 문제에 도구가 필요하다"고 가정하고 "잘 부르는가"를 잰다. When2Tool은 "부를지 말지"를 잰다. 도구 응답은 전부 로컬에서 시뮬레이션해서 API 비용 0. 라벨이 모델마다 다르다는 점을 꼭 강조.

시도 1: "비싸니까 아껴 써" 프롬프트

"필요할 때만"은 지시 없음과 거의 같은 자리. "아껴 써"는 쉬운 문제보다 어려운 문제에서 정확도를 더 잃는다. Qwen3-4B 기준, 호출 하나를 줄일 때 잃는 정확도가 어려운 문제에서 2.5배.

§3.2 Finding 2·4, Table 2, Table 8 (2,250문제, 3회 평균)
Finding 2, 4 버튼을 눌러 점을 옮겨 보여준다. 포인트 두 개: (1) 프롬프트는 쉬운 것, 어려운 것 가리지 않고 호출을 줄인다. (2) 모드 하나가 점 하나라서 "호출 예산 30% 줄이기" 같은 미세 조절이 안 된다. Llama는 "도구 쓰지 마"라고 해도 3,000번 넘게 부른다는 것도 재밌는 포인트(모델 선택 바꿔서 보여주기).

재학습 없음

모델 가중치도, forward pass도 건드리지 않는다. 응답 앞부분만 미리 채운다(prefill).

τ 하나로 조절

p를 자르는 문턱값 τ를 올릴수록 "혼자 풀 수 있음" 판정이 늘어 호출이 준다. 프롬프트와 달리 원하는 만큼 돌릴 수 있는 손잡이 (Qwen 기준).

soft와 hard

soft는 문장만 넣어서 모델이 반대할 여지를 둔다. 지시를 잘 안 듣는 Llama에는 출력 형식 자체를 강제하는 hard prefill이 필요했다.

§5.1, 부록 E.1
방법 3단계: hidden state 뽑기 → probe로 p 계산, τ와 비교 → 첫 문장 prefill. 다른 steering 기법(activation addition 등)과 달리 forward pass를 안 건드리니 어떤 서빙 인프라에도 붙는다. hard prefill은 직답이면 "\boxed{", 도구면 tool-call JSON의 시작 부분을 강제로 채운다.

쓸 수 있는 조건

  • hidden state를 읽을 수 있어야 한다. 오픈 웨이트 모델을 직접 띄워야 한다. API로만 쓰는 모델에는 지금 형태 그대로는 못 쓸 것이다 (발표자 추론).
  • 모델마다 probe와 라벨을 새로 만들어야 한다. 모델이 바뀌면 다시.
  • 지시를 잘 안 듣는 모델(Llama)은 soft prefill을 부분적으로 무시해서, 출력 형식을 강제해야 했다.

아직 열린 질문

  • When2Tool로 학습한 probe를 실제 QA에 그대로 옮기면 AUROC 0.67–0.80. 깔끔한 벤치마크 밖에서는 신호가 약해진다.
  • 저자들도 인정: probe가 "문제가 어려워 보이는지" 같은 표면 단서와 독립적이라는 건 증명하지 못했다.
  • 실험은 1.7B–70B 오픈 모델까지. 더 큰 최신 모델에서도 같은지는 모른다.

그래서 우리 에이전트에는? 제안

1. 먼저 재 보기

로그에서 도구를 부른 요청을 골라 도구 없이 다시 돌려 본다. 맞힌 비율이 곧 우리 에이전트의 "낭비 호출" 비율. 논문의 라벨 방식 그대로다.

2. 오픈 모델을 쓴다면

라벨 수백 개와 로지스틱 회귀 하나면 시험해 볼 수 있다. 코드도 공개돼 있다.
